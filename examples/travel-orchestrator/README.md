# Travel Orchestrator

Asks the minimal questions, then plans transport, stay, itinerary, local transport, tickets, and return — all validated through MCP search.

Mirrors the `stock-analysis` example layout:

```text
travel-orchestrator/
├── agent.yaml            # agent definition (model, prompts, skills, MCP)
├── prompts/system.md     # role, intake rules, orchestration, research standards
├── mcp/configs.json      # 4 MCP servers: keyless (exa, trivago, kiwi) + keyed (booking)
└── skills/
    ├── trip-intake/      # one-round, max-9-questions intake (essentials + preferences + catch-all)
    └── render-html-page/ # trip → polished self-contained HTML page (owns the design system)
```

`mcp:<server>` skills (`mcp:exa`, `mcp:kiwi`, `mcp:booking`, `mcp:trivago`) are generated by the keen harness at runtime from `mcp/configs.json` — never hand-write or commit them under `skills/`. The only hand-written skills are `trip-intake` and `render-html-page`.



## Run it

```bash
keen-agent --agent ./examples/travel-orchestrator/agent.yaml
keen-agent validate --agent ./examples/travel-orchestrator/agent.yaml
```

Try: "Create a trip for Amsterdam." The agent asks one batched round (dates, origin, party, budget, transport/stay leanings, interests + pace, food/stay must-haves, plus an open catch-all for additional requirements) with defaults, confirms a ≤6-line brief, runs the transport / stay / itinerary tracks via the harness-generated MCP skills, then composes the connected plan and saves it as a polished HTML page in build mode.

## Live data — MCP servers

| Server | What it gives | Auth | Tools |
|---|---|---|---|
| `exa` | Web search + page fetch: rail timetables, opening hours, ticket shops, verification | none | `web_search_exa`, `web_search_advanced_exa`, `web_fetch_exa` |
| `trivago` | Hotel price comparison with deep links to booking partners | none — https://mcp.trivago.com/mcp | `trivago-search-suggestions`, `trivago-accommodation-search`, `trivago-accommodation-radius-search` |
| `booking` | Booking.com stays for exact dates/party with property `url`, price, scores | `x-api-key` — free key at https://app.hasdata.com/sign-up (no card, ~100 calls trial) | search stays, property details |
| `kiwi` | Official Kiwi.com flight search: one-way/round-trip, ±3-day flex, all cabins, booking links | none — https://mcp.kiwi.com (`search-flight`) |

`mcp/configs.json` ships with one keyed server (`booking` via HasData). Replace the
placeholder with a real key; never commit real keys. Until you do, the agent says so
once and falls back to the keyless servers, marking hotel prices
"unverified — re-check before booking". Flights, rail verification, tickets, and
hotel comparison run keyless (`kiwi`, `exa`, `trivago`). Tickets are researched with Exa on official attraction/museum pages and official ticket shops. Booking MCPs are flaky: on any `kiwi` / `booking` / `trivago` failure, timeout, or empty result the agent retries once, then falls back to Exa search for the same data and marks those facts "unverified — re-check before booking".

Kiwi.com hosts the server itself (built with Alpic AI, repo `alpic-ai/kiwi-mcp-server-public`
holds install docs only), so there is nothing to install locally.

## Clickable URLs for the user

Every flight, stay, and ticket recommendation carries one URL the user can open directly:
airline/booking deep link (flights), Booking.com property `url` or cheapest trivago partner
link (stays), official attraction/ticket-shop page verified via Exa (tickets). EU rail has no public search MCP, so rail legs link the
operator timetable (NS/DB/SNCF/Eurostar) verified via Exa. Free walking tours via GuruWalk
and museum editorial (e.g. Monday-closure traps) via travel.art, both through Exa fetch.

Research rule from `prompts/system.md`: official source first, no invented numbers, every
claim cited with URL + retrieved date.
